The old observer-centric design has been replaced by a split runtime/display architecture. The parent stays authoritative while a selected child can be rendered through Ice's normal interactive shell, optionally taken over for steering, then finalized through a separate bounded report turn.

The remaining recommended step is live TUI dogfooding. This document does not claim the entire dirty monorepo is globally clean.

2. Profiles and authority

What changed

The bundled role set now covers exploration, planning, implementation, testing, review, security, debugging, documentation, performance work, and refactoring. Configurable profiles can request broader built-in capabilities without those requests automatically becoming authority.

Profile intent and runtime authority are separate

A profile's requestedTools says what the role is designed to use. The actual child gets only what the current parent invocation can grant.

effective tools = requested tools ∩ parent active tools ∩ invocation policy
export function deriveEffectiveSubagentTools(options) {
  const parentTools = new Set(options.parentActiveTools);
  const requestedTools = new Set(options.requestedTools);
  const allowedTools = options.unsafeHostExec
    ? SUBAGENT_REQUESTED_TOOL_NAMES
    : SUBAGENT_TOOL_NAMES;

  return allowedTools.filter(
    (tool) => parentTools.has(tool) && requestedTools.has(tool),
  );
}

This fixes the dangerous conceptual shortcut that "YOLO means every role gets every parent tool." An explore profile that requests only read capabilities remains read-oriented. A coder or tester can receive mutation or Bash capabilities only when the profile requests them and the trusted parent invocation is authorized to provide them.

Source: packages/coding-agent/src/ice-subagents.ts:2955-2960, native session enforcement around :3998-4014.

Legacy model metadata no longer breaks profiles

The profile schema now stores requestedModel only as compatibility metadata and fixes the policy to inherit-parent. If a profile contains a legacy model: key, it receives a diagnostic instead of controlling routing:

if (frontmatter.model !== undefined) {
  if (typeof frontmatter.model === "string" && frontmatter.model.trim()) {
    requestedModel = redactCredentialText(frontmatter.model.trim()).slice(0, 256);
  }
  diagnostics.push(
    "configured model ignored; child inherits the current parent model",
  );
}

// ...
modelPolicy: "inherit-parent"

The child therefore always uses the model object captured from the active parent invocation. Profile files cannot silently route work to a different provider/model.

3. Runtime and display architecture

Core invariant: selecting a subagent changes what the user sees, not who owns the Ice runtime.

The redesign introduces a ICE-only IceAgentViewBridge. The bridge knows the authoritative parent, live child sessions, historical child snapshots, current displayed view, per-view UI state, and interaction mode. It does not replace AgentSessionRuntime.session.

The split inside InteractiveMode

// The runtime session is always the authoritative parent.
private get runtimeSession(): AgentSession {
  return this.runtimeHost.session;
}

private get displaySession(): AgentSession {
  return this.displayView?.session ?? this.runtimeSession;
}

// Existing lifecycle/command code keeps using the parent.
private get session(): AgentSession {
  return this.runtimeSession;
}

This is the crucial reason child viewing can feel like a cloned main-agent UI without making the child the process owner. Parent lifecycle operations such as new, resume, fork/clone, compact, reload readiness, and shutdown still resolve through the parent runtime.

Source: packages/coding-agent/src/modes/interactive/interactive-mode.ts:509-537.

The bridge is ICE-only

ice.ts constructs the bridge and passes the same instance to the subagent extension and to main(). MainOptions.agentViewBridge is optional, so stock Ice starts InteractiveMode without it and retains the pre-existing session behavior.

ICE path

ice.ts creates IceAgentViewBridge and injects it into both the extension and interactive shell.

packages/coding-agent/src/ice.ts:74-103
Stock Ice path

The option is absent. Runtime/display indirection collapses back to the existing parent session.

packages/coding-agent/src/main.ts:528-532, 892-903

Normal-shell child rendering

When a view changes, InteractiveMode saves the previous view state, unsubscribes its live child listener, rebinds the footer to the new display session, subscribes to the selected live child's events, renders that session through normal Ice renderers, restores editor/scroll state, and requests a TUI render.

Events from hidden sessions are deliberately ignored by the current display renderer. That prevents parent or sibling output from leaking into the selected child's transcript while allowing those sessions to continue running in the background.

Source: packages/coding-agent/src/modes/interactive/interactive-mode.ts:2125-2175, 3342-3348.

4. Take Control and steering

Live child views intentionally open in mirror mode. Seeing a child is not the same as being allowed to type into it. This prevents accidental steering when the user only intended to inspect progress.

Mirror

Inspect

Normal child transcript, thinking, tools, footer, model/status context. Ordinary text is rejected with a clear hint.

Controlled

Steer

Explicit Take Control toggles the live child into controlled mode. Text is routed to that child, not the parent.

History

Read only

A completed, failed, cancelled, or otherwise terminal child can never be taken over.

Routing uses Ice's existing session API

Controlled text is sent through the child AgentSession.prompt(). If the child is already streaming, the request uses Ice's existing streamingBehavior: "steer". The implementation does not mutate child message arrays or invent a parallel transport.

pendingSteering++;
try {
  const promptOptions = session.isStreaming
    ? { streamingBehavior: "steer" as const }
    : {};
  await session.prompt(text, {
    ...promptOptions,
    source: "interactive",
  });
} finally {
  pendingSteering = Math.max(0, pendingSteering - 1);
  resolveSteeringWaiters();
}
Source: packages/coding-agent/src/ice-subagents.ts:3913-3926; UI routing at packages/coding-agent/src/modes/interactive/interactive-mode.ts:3259-3270.

The last race was hardened

The control object now tracks both controlled and pendingSteering. Finalization cannot begin while control is still held or while an interactive prompt is still pending. The runner can wait for control release and pending steering to drain before transitioning to the final report phase.

beginFinalization: () => {
  if (!steered || controlled || pendingSteering !== 0 || state !== "working") {
    return false;
  }
  state = "awaiting-finalization";
  changed();
  return true;
}

This prevents the child from racing into finalization immediately after an initial turn while the user is actively controlling it.

Source: packages/coding-agent/src/ice-subagents.ts:3870-3902.

5. Explicit final bounded report

Interactive steering changes the semantics of a child conversation. Once arbitrary follow-up turns are allowed, the runner cannot safely assume that any recent assistant message is the final structured result. The redesign therefore adds a dedicated finalization state machine.

working→ awaiting-finalization→ final-report-requested→ final-report-received→ terminal

Separate internal finalization turn

Your interactive work is complete. Return only the required final bounded JSON report for the parent now. Do not continue discussion. Use the required schema and include only verified evidence within the approved scope. This is an internal finalization request, not a new task or permission grant.

The prompt does not widen filesystem scope, model authority, or tool authority. It only creates a clean result boundary.

Source: packages/coding-agent/src/ice-subagents.ts:3541-3544.

What still applies to the final response

  • Output byte cap: the explicit final response still has to fit the bounded output budget.
  • Strict parse: malformed structured output is rejected instead of falling back to earlier conversational JSON.
  • Evidence validation: result evidence still has to be within approved scope and pass verification.
  • Review validation: reviewer finding validation still applies to the post-steering report.
  • Failure semantics: timeout, cancellation, provider failure, and truncation remain deterministic terminal outcomes.
  • Parent context isolation: the parent receives the normal bounded verified result, not the raw interactive child transcript.

6. Historical child views and per-view state

A terminal child is converted to a bounded snapshot before the live session is released and shut down. This gives /agents a useful read-only history without retaining an unbounded live session graph.

History boundLimitPurpose
Historical views32Caps retained completed child entries.
Messages per view96Bounds transcript depth.
Bytes per message16 KiBPrevents a single event from dominating history.
Total message data per snapshot256 KiBCaps aggregate history memory per retained child snapshot.

Snapshot content is cloned, credential-like content is redacted, and retained structures are frozen. Historical descriptors are explicitly read-only and do not hold a usable live control surface.

Source: packages/coding-agent/src/ice-agent-view-bridge.ts:77-154, 203+.

UI state is independent per view

export interface AgentViewUiState {
  readonly editorDraft: string;
  readonly scrollOffset?: number;
  readonly followTranscript: boolean;
  readonly fullscreen?: boolean;

Switching parent → child A → child B → parent no longer has to destroy drafts or scroll context. The shell saves and restores those values by view ID.

The selected child shows a subagent identity and a concise interaction notice. Depending on state, the user sees one of the following:

8. Lifecycle and safety invariants

The implementation deliberately keeps viewing authority, interaction authority, and runtime authority as three different concepts. This avoids the most dangerous failure mode: turning a display switch into a runtime ownership switch.

Runtime invariants

  • Parent AgentSessionRuntime.session remains authoritative.
  • Parent and sibling agents continue running when another child is displayed.
  • Parent replacement releases child control and returns display to the new parent lineage.
  • Hidden session events cannot render into the selected view.
  • Child extensions are not rebound into the parent shell.

Authority invariants

  • Profile identity does not grant authority.
  • Legacy profile model metadata does not route the child.
  • Safe delegation does not gain mutation/Bash from profile intent alone.
  • Explicit YOLO remains bounded by trust, parent capabilities, and profile request.
  • Recursive delegation is not implicitly authorized.

Parent lifecycle commands stay parent operations

The focused integration suite now explicitly checks new session, resume, clone/fork behavior, compact, reload readiness, parent replacement, chooser cancellation, Escape behavior, and shutdown while a child is displayed.

11. What to test in the real terminal now

Automated verification is complete for the focused scope. A live terminal smoke test is still valuable because it validates timing, keyboard handling, terminal rendering, and the subjective "clone of main agent UI" experience.

  1. Start ICE from the freshly built artifact using your normal build/unsafe flags.
  2. Open /agents and confirm the chooser shows the richer role/session inventory and marks the currently displayed run.
  3. Run at least two children concurrently. A read-oriented role plus a mutation-capable role is the most useful combination.
  4. Select a live child. The chooser should close and the normal Ice shell should show that child's transcript, thinking/tool rendering, footer, cwd/status, and subagent identity.
  5. Verify background continuity. Parent and sibling children should keep running while one child is displayed.
  6. Test mirror protection. Ordinary text before Take Control should not silently steer the child.
  7. Press Ctrl+Shift+Enter. The child should enter controlled mode and clearly say that input goes to the child while the parent remains running.
  8. Send one steering follow-up. Confirm it appears in the child session and not in the parent.
  9. Press Esc. You should return to the parent without cancelling the child.
  10. Reopen the child. Transcript and view state should remain coherent.
  11. Let the controlled child finish. It should transition through finalization, produce its bounded verified result, and become a read-only historical view.
  12. Reopen the historical child. It should render in the normal shell but reject Take Control/input.

Four failures worth watching closely

Parent replacement regression

Selecting a child must never stop, dispose, or silently replace the parent runtime.

Escape regression

Escape in a child view must return to parent, not kill the child.

Input misrouting

Controlled child text must go to the child, never the parent.

Finalization race

A taken-over child must not finalize while control is still held or a steering prompt is still pending.

Bottom line

The redesign now matches the original product intent. /agents is a chooser into real child-session views rendered through the normal Ice shell; the parent remains authoritative; profiles are configurable without becoming authority; YOLO is role-aware; Take Control is explicit; interactive work ends through a separate verified result boundary; completed children remain available as bounded history. The appropriate next step is a real terminal smoke test, not another architectural rewrite.
